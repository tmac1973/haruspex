# Phase 01 — Keyword candidates in Rust

**Depends on:** nothing · **Enables:** the `search_code` tool (phase 04) and
the embedding index's chunking (phase 07)

## Goal

A Rust command, `code_search_candidates`, that turns a plain-words query into
the top chunks of a folder's files, ranked by keyword score. It is the spike's
Python candidate stage moved next to `code_grep`, so it walks files the same
gitignore-aware, WSL-aware way. No UI and no tool yet; it ships tested and
unused.

## Steps

1. **Query terms** (`fn query_terms(query: &str) -> Vec<String>`): split on
   non-identifier characters, then split each identifier on camelCase and
   snake_case boundaries, keeping the whole identifier too
   (`autosizeTextarea` → `autosizetextarea`, `autosize`, `textarea`).
   Lowercase, drop words under 3 characters and this stopword list: `the and
   for from with are its this that which where what when how does want into
   all their them they who user users app code file files there make sure
   still before after while`; then strip one
   suffix (`ing`, `ed`, `es`, `s`) from words longer than 5 characters. Keep
   order, drop duplicates, cap at 12 terms.
2. **Files**: resolve the root with `resolve_code_root` and walk it (or `path`
   under it) with `walk_files`, as `code_grep` does. Skip files over 1 MB, files
   whose first 8 KB contain a NUL byte, and lockfiles by name
   (`package-lock.json`, `Cargo.lock`, `yarn.lock`, `pnpm-lock.yaml`,
   `bun.lockb`, `poetry.lock`, `uv.lock`). Read as UTF-8 lossily.
3. **Chunks**: 30-line windows starting every 15 lines (half-overlapping),
   lines 1-indexed. A file shorter than 30 lines is one chunk.
4. **Score**: a chunk's matched terms are those that appear (case-insensitive,
   substring) in its text or its path. With `N` = chunks that matched any term
   and `df(t)` = chunks containing `t`, score =
   `Σ ln(1 + N / df(t))` over matched terms `+ 0.3 · ln(1 + hits)`, where
   `hits` counts term occurrences in the text plus twice those in the path.
   Multiply by 0.5 when the path is a test or generated file: it matches
   `*.test.*`, `*.spec.*`, `*_test.*`, `/tests/`, `/__tests__/`, `/gen/`,
   `/generated/`, or `*.min.js`.
   Step 2 lives in `pub(crate) fn candidate_files(root, path, wsl_distro)` and
   step 3 in `pub(crate) fn chunk_file(path, text) -> Vec<Chunk>`, so phase
   07 lists and chunks files exactly the same way. Scoring (step 4) runs over
   all chunks at once, since it needs `N` and `df(t)`.
5. **Pick**: sort by score, then keep a chunk only if it doesn't overlap a kept
   chunk in the same file (start lines under 30 apart). Stop at `limit`
   (default 100, max 200).
6. **Command**:
   `code_search_candidates(root, query, path?, limit?, wsl_distro?) -> SearchCandidates`
   with `#[ts(export)]` structs:
   `SearchCandidates { terms: Vec<String>, chunks: Vec<SearchChunk>, files_scanned: u32 }`
   and `SearchChunk { path: String, start_line: u32, end_line: u32, text: String, score: f32 }`.
   Paths relative to the root with `/` separators, as `code_grep` returns.
   Run the walk in `spawn_blocking`.
7. Run `./scripts/export-ipc-types.sh`.

## Test plan

Unit tests in `rank.rs` over a temp folder:

- `query_terms` splits camelCase and snake_case, drops stopwords, stems, caps.
- Chunk boundaries: a 70-line file gives windows at 1, 16, 31, 46, 61.
- A chunk matching two rare terms outranks one matching a common term many
  times.
- A path hit counts (`autosize.ts` ranks for "autosize" with no body hit).
- A test file ranks below the same text in a source file.
- `.gitignore`d, binary, oversize and lockfiles are skipped.
- Overlapping windows in one file collapse to the best one.
- `path` limits the walk; `limit` caps the count.

Manual: run it on the Haruspex checkout with the spike's ten questions (a
`#[ignore]`d test that prints ranks) and check the right file is in the top 100
for each; the spike had all ten.
