# Phase 17 — Measurements that decide the design

**Depends on:** nothing · **Enables:** 18–25. Every later phase has a branch
that one of these measurements settles.

## Why this phase exists

The 2026-09-30 spike (`spike-2026-09-30-dit-models.md`) justified abandoning
the SDXL + IP-Adapter + chroma-key design for sheets of sprites generated by a
DiT model with alpha. It did not answer five questions the new design depends
on, and lesson 13 of `TODO.md` applies: one sample proves little, so each is
answered with fixed seeds and counted, not eyeballed.

No Haruspex code changes in this phase. The deliverable is a measurements file
in this folder; the scripts stay in `~/Projects/asset-spike/`.

## Goal

A written answer, with numbers, to each question below — including "it does
not work", which is an answer.

## Steps

### 1. Does the transparent start work for single sprites?

Sheets are the main path, but phase 21 regenerates a failed cell as a single
sprite. The spike only measured the transparent start on sheets.

Run the eight sprite subjects from `batch.py` at seeds 1–3, denoise 0.9, 1024.
Record transparent fraction, soft-edge fraction, and whether the subject is
the right one. **Pass:** ≥ 22 of 24 transparent, subject correct by eye.

### 2. Which sheet size cuts reliably?

Nine per sheet cut exactly 5 of 12 times on Ming. Fewer subjects may lay out
more reliably, and more may amortise the text-encode cost better.

Grids of 2×2, 3×3 and 4×4 at 1024 and 2048, the items list and the top-down
list, seeds 1–4 each. Record exact-count rate, and for each miss whether it
was a duplicate, a missing subject or a merge. **Decides:** phase 21's default
sheet size. A size whose exact-count rate is below 75% is not the default.

### 3. How do sheets stay consistent with each other?

A 60-sprite set is seven sheets. Nothing yet makes sheet 4 match sheet 1.
Compare, on the same eighteen subjects split into two sheets:

- **a. Prompt only.** Same style line, same seed policy.
- **b. Prompt plus palette.** (a), then both quantized to the palette of
  sheet 1 — the mechanical layer that already exists.
- **c. Reference image.** Sheet 1 fed into sheet 2 through
  `TextEncodeMingImageEdit` as a style reference. The spike's reference
  attempt on Qwen returned the reference itself; try the phrasing "new
  subjects, drawn in the style of `<image1>`" and a reference made from a
  cropped cell rather than the whole sheet.

Measure with the existing palette-distance check (sheet 2's assets against
sheet 1's palette) and by eye on a side-by-side. **Decides:** phase 22's
cross-sheet mechanism. If only (b) works, that is the design, and (c) is
recorded as tried.

### 4. Can the bundled engine run it?

stable-diffusion.cpp documents Ming-Image with RGBA output (`docs/ming_image.md`)
and supports int8 convrot weights. The pinned build (`master-890-74988b2`)
predates it.

- Fetch the current release with `scripts/fetch-sdcpp.sh` at a bumped version
  into a scratch directory, not `src-tauri/binaries/`.
- Run a sheet through `/sdapi/v1/img2img` with a transparent RGBA
  `init_images` and `denoising_strength` 0.9. Does alpha survive the A1111
  route's image handling? If not, try the native `/sdcpp/v1/img_gen`.
- Record peak VRAM and RAM with the text encoder offloaded, and time per sheet.

**Decides:** whether phase 24 is a version bump or a new request path, and
what the hardware floor is.

### 5. What is the hardware floor?

Phase 19 drops SD1.5 and SDXL only if Ming runs on the machines SD1.5 served.
Measure Ming int8 plus the w4a8 encoder on an 8 GB card, or on this card with
VRAM capped (`--reserve-vram` in ComfyUI). Record whether it runs, and
seconds per sheet. **Decides:** whether SDXL stays in the catalogue as a
low-VRAM fallback (phase 19, step 4).
