# Phase 02 — Install manifest: launch what was installed

**Depends on:** nothing · **Enables:** Phases 03, 04, 05 (they read and write
the manifest)

## Goal

Record what was installed in a manifest inside the server folder, and launch
from it instead of from the current catalog entry. This fixes today's silent
breakage on its own: after a release changes an entry's `bin`, `args`, `env` or
`defaultTools`, an existing install keeps launching exactly as it was
installed. Existing installs get a manifest on first use.

## Steps

1. Define `InstallManifest { schema: u32 (= 1), entry: CatalogEntry,
   package_files: Vec<String>, installed_at: String (RFC 3339) }`,
   `#[ts(export)]`, camelCase. `entry` is the whole catalog entry as installed,
   so spawn, setup commands, optional-secret rules and `defaultTools` all read
   one consistent snapshot. `version()` returns the version inside
   `entry.acquisition` (npm and PyPI `version`, binary `version`). File name:
   `MANIFEST_FILE = ".haruspex-install.json"`.
2. In `McpInstaller::install`, after `install_into` succeeds and before the
   rename: list the staging folder's top-level names as `package_files`, add
   `MANIFEST_FILE`, and write the manifest with the current entry.
3. `manifest::load_or_backfill(dir, current_entry: Option<&CatalogEntry>)`:
   - If the file exists, return it.
   - If not and there is no current entry, return the existing "no catalog
     entry named …" error.
   - Otherwise build one from the current entry, replacing the version in its
     acquisition with what is on disk:
     - npm: `version` from `dir/node_modules/<package>/package.json`;
     - PyPI: under `dir/venv/**/site-packages/`, the `*.dist-info` folder whose
       name before the first `-` matches the package when both are normalised
       the PEP 503 way (lowercase, runs of `-`, `_`, `.` become `-`); read the
       `Version:` line of its `METADATA`;
     - binary: the current pin.
     If the on-disk version cannot be read, keep the pin.
   - `package_files` for a backfill: npm `node_modules`, `package.json`,
     `package-lock.json`; PyPI `venv`; binary every top-level name except the
     `filename` of the entry's `File` setup steps. Always add `MANIFEST_FILE`.
     The binary rule is safe only while no binary entry has a `Command` setup
     step (which could write other state into the folder); a test on the
     bundled catalog holds that, so a curator adding one has to revisit the
     rule.
   - Write it, so the backfill runs once.
4. `build_spawn_config` (Catalog branch) loads the catalog, calls
   `load_or_backfill(dir, catalog.entry(entry_id))`, and passes
   `&manifest.entry` to `catalog_spawn_config`. A server whose entry left the
   catalog therefore still launches from its manifest. `catalog_command_args`
   does the same, so setup commands also use the installed entry.
5. `mcp_installed_manifests` returns `load_or_backfill` for every catalog server
   whose folder exists; servers without a folder or without a loadable manifest
   are left out of the map.
6. Run `./scripts/export-ipc-types.sh`.

## Test plan

- Rust: install into a temp dir with a test catalog, then change the entry's
  `bin`, `args`, `env` and `defaultTools`; `build_spawn_config` still yields
  the original values. Remove the entry from the catalog; it still launches.
- Rust: backfill reads an npm version from a fake `package.json` and a PyPI
  version from a fake `My_Pkg-1.2.0.dist-info/METADATA` for package
  `my-pkg`; a binary uses the pin; an unreadable version keeps the pin; the
  file is written once; `package_files` follow the rules above.
- Rust: no binary entry in the bundled catalog has a `Command` setup step.
- Vitest: `startMcpServer` registers the manifest's `defaultTools`, not the
  entry's; the row uses the manifest for a server that never started.
- Manual: with a Playwright install from before this change, launch the dev
  build; `.haruspex-install.json` appears with version 0.0.83 and the server
  starts.
